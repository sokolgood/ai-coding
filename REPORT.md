# Отчет по реализации AI Coding Agent

## Цель и постановка задачи

Разработана автоматизированная агентная система для полного цикла разработки программного обеспечения (SDLC) внутри GitHub. Система имитирует работу разработчика и ревьюера: анализирует GitHub Issues, вносит изменения в код, создает Pull Requests, интегрируется с CI/CD и выполняет автоматический code review. Все действия выполняются через GitHub API и GitHub Actions workflows.

## Подход и ключевые идеи

### Application Layer (Workers)

Система построена на трех независимых workers, каждый из которых отвечает за отдельную фазу SDLC:

- **`CodeWorker`**: Обрабатывает GitHub Issues, создает/обновляет ветки, запускает `CoderAgent` для реализации задачи, коммитит изменения и создает/обновляет Pull Requests. Отслеживает итерации через `IterationState`, встроенный в тело PR.

- **`ReviewWorker`**: Запускается на событиях `pull_request` (opened/synchronize/reopened), извлекает diff и результаты CI, запускает `ReviewerAgent` для анализа кода, публикует структурированный `ReviewReport` в виде комментария и управляет лейблами (`agent:approved` / `agent:fix`).

- **`FixWorker`**: Активируется при добавлении лейбла `agent:fix`, парсит последний review комментарий с `ReviewReport`, передает feedback в `CoderAgent` для исправлений, инкрементирует итерацию и обновляет PR.

### Schema-Guided Reasoning (SGR)

Двухфазный подход к выполнению задач, повышающий надежность и прозрачность:

- **Фаза планирования**: `SGRCoderAgent` и `SGRReviewerAgent` генерируют структурированные планы (`SGRPlan`) с использованием Pydantic моделей через `openai.chat.completions.parse()`. План содержит objective, assumptions, ordered steps с suggested tools и done criteria, risks и stop conditions.

- **Фаза выполнения**: Основные агенты (`CoderAgent`, `ReviewerAgent`) получают готовый план и выполняют его пошагово, используя доступные tools. Это снижает вероятность ошибок и делает процесс предсказуемым.

### Инструменты (Tools)

Агенты взаимодействуют с репозиторием через набор специализированных tools:

- **`update_file`**: Основной инструмент для модификации файлов. Принимает полный новый контент файла (не diff), что устраняет проблемы с форматом патчей. Атомарная запись через временный файл, валидация Python синтаксиса перед сохранением, автоматический rollback при ошибках.

- **`create_file`**: Создание новых файлов. Валидация отсутствия файла перед созданием.

- **`read_file`**, **`list_directory`**, **`grep_search`**: Инструменты для исследования репозитория.

- **`run_command`**: Отключен для агентов — runtime checks (linting/tests) выполняются в CI/CD, не агентом.

Все tools защищены от path traversal через `os.path.commonpath` валидацию.

### RepoContext

Структурированный контекст репозитория, передаваемый агентам:

- **`tree_summary`**: Структура директорий верхнего уровня
- **`readme`**: Первые 50 строк README.md
- **`agents_md`**: Содержимое AGENTS.md (если существует) — правила репозитория, которые агенты обязаны соблюдать
- **`build_files`**: Информация о build файлах (pyproject.toml, requirements.txt, etc.)
- **`tests_hint`**: Конфигурация тестов (pytest.ini, tox.ini, структура tests/)

`RepoContextBuilder` автоматически собирает эту информацию при запуске агента.

### Итерации и защита от циклов

Многоуровневая защита от бесконечных циклов:

- **`IterationState`**: Хранится в скрытом HTML-комментарии в теле PR (`<!-- agent:issue=42 iter=2 max=5 -->`). Позволяет отслеживать количество итераций между Code → Review → Fix циклами и восстанавливать состояние при повторных запусках.

- **Максимум итераций на уровне Issue**: По умолчанию 5 итераций на Issue (настраивается через `--max-iter`). При достижении лимита система выбрасывает исключение.

- **Лимиты tool calls**: `CoderAgent` — максимум 20 tool call итераций, `ReviewerAgent` — 10. При достижении лимита агент завершает работу с summary текущего прогресса.

- **Stop conditions в SGR планах**: SGR агенты генерируют stop conditions, которые могут прервать выполнение досрочно.

### Observability через Langfuse

Полная трассировка всех операций системы для отладки и анализа:

- **Интеграция**: Использование декоратора `@observe()` из `langfuse.decorators` на всех критических точках системы
- **Трассируемые компоненты**:
  - `LLM.invoke()`: все запросы и ответы с полными промптами, параметрами модели, токенами
  - Агенты (`CoderAgent.run`, `ReviewerAgent.run`, `SGRCoderAgent.run`, `SGRReviewerAgent.run`): входные контексты, результаты выполнения, trace_id для связывания операций
  - Все tools (`update_file`, `create_file`, `read_file`, `list_directory`, `grep_search`, `apply_patch`, `run_command`): параметры вызовов, результаты, ошибки
- **Graceful degradation**: Если Langfuse ключи не заданы, система работает без observability, без ошибок
- **Преимущества**: Полная видимость работы агентов, возможность анализа паттернов ошибок, оптимизация промптов на основе реальных данных, отладка сложных кейсов

## 🔄 Пайплайн работы

### Полный цикл: Issue → Code → Review → Fix

```
┌─────────────┐
│ GitHub Issue│
└──────┬──────┘
       │
       ▼
┌─────────────────┐
│  Code Agent     │
│  (SGR Planning) │
└──────┬──────────┘
       │
       ├─► SGRCoderAgent: генерирует план
       │
       ├─► CoderAgent: выполняет план
       │   ├─► read_file
       │   ├─► update_file
       │   └─► create_file
       │
       ▼
┌─────────────────┐
│  Pull Request   │
│  (iteration=1)  │
└──────┬──────────┘
       │
       ▼
┌─────────────────┐
│ Review Agent    │
│ (SGR Planning)  │
└──────┬──────────┘
       │
       ├─► SGRReviewerAgent: генерирует план ревью
       │
       ├─► ReviewerAgent: выполняет ревью
       │   ├─► read_file (измененные файлы)
       │   ├─► grep_search (поиск паттернов)
       │   └─► генерирует ReviewReport
       │
       ▼
┌─────────────────┐
│ Review Comment  │
│ verdict: FAIL   │
│ + лейбл:fix     │
└──────┬──────────┘
       │
       ▼
┌─────────────────┐
│  Fix Agent      │
│  (использует    │
│   CoderAgent)   │
└──────┬──────────┘
       │
       ├─► Парсит ReviewReport из комментария
       ├─► Форматирует feedback
       ├─► CoderAgent: исправляет код
       │
       ▼
┌─────────────────┐
│  Pull Request   │
│  (iteration=2)   │
└──────┬──────────┘
       │
       ▼
┌─────────────────┐
│ Review Agent    │
│  (повторно)     │
└──────┬──────────┘
       │
       ▼
┌─────────────────┐
│ Review Comment  │
│ verdict: PASS   │
│ + лейбл:approved│
└─────────────────┘
```

**Больше деталей в README.md!**

**Основные этапы**:
1. **Issue создан** → GitHub Actions workflow запускает `CodeWorker`
2. **Code Agent** → Создает ветку, генерирует SGR план, выполняет реализацию, коммитит и создает PR
3. **PR создан/обновлен** → Автоматически запускается CI/CD pipeline
4. **Review Agent** → Анализирует diff, учитывает CI результаты, публикует review комментарий и управляет лейблами
5. **Если вердикт FAIL** → Добавляется лейбл `agent:fix`, GitHub Actions запускает `FixWorker`
6. **Fix Agent** → Парсит review feedback, исправляет код, инкрементирует итерацию, обновляет PR
7. **Цикл повторяется** до получения `agent:approved` или достижения max_iter

## Эксперименты и важные технические решения

### 1. UpdateFileTool: Full-Content подход вместо Diff

**Проблема**: Изначально использовался подход, где LLM генерировал unified diff патчи, которые затем применялись через `git apply`. Это приводило к частым ошибкам из-за:
- Неправильного формата патчей от LLM
- Несовпадения контекста (файл изменился между read и apply)
- Проблем с CRLF/LF и whitespace
- Хрупкости `git apply` даже для идеальных патчей

**Решение**: Переход на "FILE-FIRST" подход, используемый в Cursor, Claude Code и Copilot Workspace:
- LLM генерирует **полный новый контент файла** (не diff)
- Агент атомарно перезаписывает файл через временный файл и `Path.replace()`
- Diff генерируется программно через `difflib.unified_diff` только для логов/PR
- Валидация Python синтаксиса через `ast.parse()` перед сохранением
- Автоматический rollback при синтаксических ошибках

**Результат**: Резкое снижение ошибок при модификации файлов, стабильность операций.

### 2. Path Traversal Protection

**Проблема**: Изначальная проверка `base_resolved in file_path.parents` могла давать ложные совпадения при похожих путях.

**Решение**: Использование `os.path.commonpath` для строгой проверки:

```python
common = os.path.commonpath([str(base_resolved), str(file_path)])
if common != str(base_resolved):
    return ToolResult(success=False, error="Path traversal not allowed")
```

Это гарантирует, что файл находится строго внутри `base_path`, без edge-cases.

### 3. Разделение ответственности: CI/CD отдельно от агентов

**Проблема**: Если агент запускает тесты/linters, это создает:
- Зависимости от окружения (нужно устанавливать зависимости)
- Риск бесконечных циклов (агент пытается исправить linting ошибки)
- Дублирование с CI/CD

**Решение**:
- `run_command` tool отключен для всех агентов (закомментирован в промптах)
- Явные инструкции в промптах: "Runtime checks (linting/tests) are handled by CI/CD, not by the agent"
- SGR промпты содержат правило: "DO NOT plan steps for running tests, linters, or build commands"
- `ReviewerAgent` получает `CI_CONCLUSION` через environment variable и учитывает его в анализе

**Результат**: Четкое разделение ответственности, агенты фокусируются на коде, CI/CD — на проверках.

### 4. Структурированные выходы через Pydantic

**Решение**: Все агенты возвращают структурированные данные через Pydantic модели:
- `CoderResult`: success, summary, files_modified
- `ReviewReport`: verdict, summary, changes (с severity), positives, risks
- `SGRPlan`: objective, steps, assumptions, risks, stop_conditions

Используется `openai.chat.completions.parse()` для прямого парсинга в Pydantic, что гарантирует корректный формат и валидацию.

### 5. Управление лейблами в ReviewerAgent

**Решение**: `ReviewWorker` автоматически управляет лейблами на основе вердикта:
- `verdict == "PASS"` → добавляет `agent:approved`, удаляет `agent:fix`
- `verdict == "FAIL"` → добавляет `agent:fix`, удаляет `agent:approved`

Перед удалением лейблов проверяется их наличие на PR (через `pr.get_labels()`), чтобы избежать 404 ошибок от GitHub API.

### 6. Observability через Langfuse

**Проблема**: При работе с LLM-агентами критически важно иметь полную видимость:
- Какие промпты отправляются в LLM
- Какие ответы получаются
- Какие tools вызываются и с какими параметрами
- Где происходят ошибки и почему
- Сколько токенов тратится на каждую операцию

**Решение**: Интеграция Langfuse через декоратор `@observe()`:
- Все LLM вызовы (`LLM.invoke`) логируются с полными промптами, параметрами, токенами
- Все агенты (`CoderAgent`, `ReviewerAgent`, SGR агенты) логируют входные контексты и результаты
- Все tools логируют параметры вызовов и результаты
- `trace_id` связывает все операции в рамках одной задачи
- Graceful degradation: если ключи не заданы, система работает без observability

**Результат**: Полная трассировка работы системы, возможность анализа паттернов, оптимизация промптов на основе реальных данных, быстрая отладка проблем.

## Результаты и метрики

### Успешное создание PR из Issue

**Реализация**: `CodeWorker` автоматически:
- Создает ветку `agent/issue-{number}`
- Запускает `CoderAgent` для реализации задачи
- Коммитит и пушит изменения
- Создает PR с `IterationState` в теле

**Валидация**: Система протестирована на реальных Issues. PR создаются корректно, содержат все необходимые метаданные для отслеживания итераций.

### CI запускается на PR

**Реализация**: После создания/обновления PR автоматически запускается CI/CD pipeline (настраивается в репозитории через GitHub Actions workflows).

**Интеграция**: `ReviewWorker` получает результаты CI через:
- Environment variable `CI_CONCLUSION` (если передано из workflow)
- GitHub API через `GitHubService.get_ci_summary()` (анализ последних workflow runs)

CI результаты передаются в `ReviewerAgent` как часть контекста и учитываются при анализе.

### Reviewer публикует комментарий и лейблы, учитывает CI_CONCLUSION

**Реализация**:
- `ReviewerAgent` генерирует структурированный `ReviewReport` через Pydantic модель
- `ReviewWorker` форматирует комментарий (человекочитаемый + скрытый JSON для машинной обработки)
- Автоматическое управление лейблами на основе вердикта
- `CI_CONCLUSION` передается в промпт и учитывается при анализе (например, если CI failed, reviewer более строго проверяет код)

**Валидация**: Review комментарии публикуются корректно, содержат:
- Вердикт (PASS/FAIL)
- Summary
- Requested changes с severity (blocker/major/minor)
- Positives и risks
- Скрытый JSON для `FixWorker`

### Max-iter / Stop conditions, лимиты tool-calls

**Реализация**:

1. **Максимум итераций на Issue**:
   - По умолчанию: 5 итераций
   - Настраивается через `--max-iter` в CLI
   - Отслеживается через `IterationState` в PR body
   - При достижении лимита: `ValueError` с сообщением

2. **Лимиты tool calls**:
   - `CoderAgent`: максимум 20 tool call итераций
   - `ReviewerAgent`: максимум 10 tool call итераций
   - При достижении лимита: агент завершает работу, запрашивает summary у LLM

3. **Stop conditions в SGR планах**:
   - SGR агенты генерируют `stop_conditions` (например, "Logging successfully implemented")
   - Могут быть использованы для досрочного завершения (в текущей реализации не реализовано автоматическое прерывание по stop conditions, но структура позволяет это добавить)

**Валидация**: Система протестирована на edge cases:
- Достижение max_iter → корректное исключение
- Достижение tool call лимита → graceful завершение с summary
- Восстановление `IterationState` при повторных запусках → корректная инкрементация

## Ограничения и что улучшить

### 1. Отсутствие автоматического прерывания по Stop Conditions

**Текущее состояние**: SGR планы генерируют `stop_conditions`, но агенты не проверяют их автоматически для досрочного завершения.

**Улучшение**: Добавить проверку stop conditions после каждого шага выполнения. Если условие выполнено, агент может завершить работу досрочно, не дожидаясь лимита tool calls.

### 2. Ограниченная обработка больших репозиторий

**Текущее состояние**: `RepoContext` собирает только верхний уровень структуры и первые 50 строк README. Для больших репозиторий это может быть недостаточно.

**Улучшение**:
- Добавить фильтрацию по релевантности (например, только файлы, измененные в PR, или файлы, упомянутые в Issue)
- Использовать embeddings для семантического поиска релевантных файлов
- Кэширование `RepoContext` между итерациями одного Issue

### 3. Нет поддержки мультифайловых изменений в одном tool call

**Текущее состояние**: `update_file` принимает только один файл за вызов. Для задач, требующих изменений в нескольких файлах, агент делает несколько последовательных вызовов.

**Улучшение**: Добавить `update_files` tool, который принимает словарь `{path: new_content}` и применяет изменения атомарно (либо все успешно, либо rollback всех).

### 4. Ограниченная интеграция с CI/CD

**Текущее состояние**: `ReviewerAgent` получает только `CI_CONCLUSION` (success/failure) и базовую информацию о workflow runs. Детальные логи CI не передаются.

**Улучшение**:
- Парсить детальные логи failed CI jobs и передавать их в `ReviewerAgent`
- Анализировать конкретные ошибки тестов/linters и включать их в `ReviewReport.changes`
- Автоматически исправлять типичные ошибки (например, formatting issues) через `FixAgent`

### 5. Нет поддержки контекста из нескольких Issues/PR

**Текущее состояние**: Система работает с одним Issue за раз. Если задача требует контекста из связанных Issues или PR, агент его не получает.

**Улучшение**: Добавить анализ связанных Issues/PR через GitHub API и включение их в контекст агента.
